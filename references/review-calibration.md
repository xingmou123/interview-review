# 真实改稿校准

以下案例根据已发生的面试复盘改稿整理，省略学员身份和文档地址。它们用于校准点评尺度，不是其他学员的项目事实，也不表示类似题目一律没有问题。

## 什么值得点评

| 场景 | 合适的处理 |
| --- | --- |
| 自我介绍已经说明经验和职责 | 写“没问题”，不因为口语重复、没有列出更多指标而强加建议。 |
| 确认设备输出什么数据的短问 | 回答已经确认即可，不要求再讲一遍完整采集链路。 |
| 面试官紧接着追问发送或接收 | 连着前后回答判断，不把整理稿里的短追问当成学员此前答偏的证据。 |
| 调试案例已经有现象、排查和原因 | 不自动追加寄存器证据、完整复测数字和所有异常分支，除非这次追问确实需要。 |
| 面试官明确问测试用例怎么设计 | 给出当前功能的正常、异常、超时和恢复用例，比提醒“完善测试”有用。 |
| 用户已经把建议改成“没问题”或主动删空 | 尊重这个判断，不把删空当漏填，不从旧稿恢复长评。 |

## 选型与资源限制

问选型时，要帮助学员从产品功能、接口、内存和算力需求讲出取舍，不能只纠正个别术语。

一份 LVGL 面试记录中，学员用常见 STM32 的资源情况举例，说明 MCU 资源较紧，再谈内存配置。原点评逐项追究 RAM 范围、分配器是否更安全，还加入整屏和分块缓冲的精确计算。这超出了当时的面试问题。

合适的补充是资源受限时怎么做：精简字体和图片、控制同时创建的控件数量、使用较小缓冲分块刷新。只有面试明确追问容量计算或分配器原理时，再展开这些内容。

## 解释要解决眼前的问题

- DMA 打印的简短追问，重点是串口等待为什么占用执行时间，以及 DMA 怎样减轻影响。不要自动扩展成日志队列、满队列策略和性能测试方案。
- 问存储抽象，可以用保存故障记录讲清上层调用什么、下面承担什么、换存储器时哪里需要变化。不要只罗列 SFUD、FAL、FlashDB 等名称。
- 问 UI 与业务怎样交互，就沿着一次操作说明谁发送请求、谁执行、结果怎么回到页面。模式名称不能代替流程。

## 减少重复引用

原答已经在建议上方时，通常直接指出缺少的内容即可。比如学员说接触过 MVVM，却没有解释，可以用文件列表讲 Model 的业务数据与操作、View 的控件显示，以及 ViewModel 的界面状态和操作入口。

没有必要再把学员那句话完整引用一次，解释它哪里不好，再用整段引号包住替换话术。需要定位问题时可以短引，示范回答可以自然另起一段。减少的是重复和固定套路，不是禁止引号。

## 技术核查与学员经历

技术依据用于判断建议是否成立，不在每题后附一串外部链接，也不把查到的例外都变成学员必须交代的内容。确属课程、且与当前问题相关的学习入口可以保留。

示例只能演示解释方法，不能据此替学员补上职责、参数或实测结果。助手自己写过的参考答案也不构成真实经历；助手改过的文字不能冒充用户已经逐句认可。
