# 真实改稿校准

以下案例根据已发生的面试复盘改稿整理，省略学员身份和文档地址。它们用于校准点评尺度，不是其他学员的项目事实，也不表示类似题目一律没有问题。

## 什么值得点评

| 场景 | 合适的处理 |
| --- | --- |
| 自我介绍已经说明经验和职责 | 写“没问题”，不因为口语重复、没有列出更多指标而强加建议。 |
| 确认设备输出什么数据的短问 | 回答已经确认即可，不要求再讲一遍完整采集链路。 |
| 面试官紧接着追问发送或接收 | 连着前后回答判断，不把整理稿里的短追问当成学员此前答偏的证据。 |
| 调试案例已经有现象、排查和原因 | 不自动追加寄存器证据、完整复测数字和所有异常分支，除非这次追问确实需要。 |
| 面试官明确问测试用例怎么设计 | 给出当前功能的正常、异常、超时和恢复用例，比提醒“完善测试”有用。 |
| 用户已经把建议改成“没问题”或主动删空 | 尊重这个判断，不把删空当漏填，不从旧稿恢复长评。 |
| 前一题问 EEPROM，后一题问互斥量，建议仍在讲 EEPROM | 逐题连读问题、回答与建议，发现错位就定位并修正；建议栏有文字不等于这道题已复盘。 |

## 明确问测试用例时，把方法与预期写齐

题目已经要求怎样测试，就按当前方案写出输入条件、制造异常的方法、预期行为和判定依据。正常、错误、边界与恢复分别回应具体风险，表格能帮助比较时可以用表格；不把同一清单追加到普通原理题后面。

例如串口单 APP 区升级，测试传输中断和写入中断时，要说明怎样让过程停在对应阶段、重启后应留在何处、怎样确认不执行未确认有效的 APP，以及重新传入正确文件能否恢复。测试预期不是已经发生的结果，也不把 A/B 回滚作为这份单区方案的现有功能。点评解释缺口，参考回答示范面试时怎样把主要用例说清楚，不重复整张表。

## 方案成立条件与代价

复杂题需要把方案怎样解决问题讲清楚，也要交代它依赖的关键条件。只展开当前方案依赖的部分，不把所有边界附加到每道原理题。

- 循环 DMA 改用独立接收块时，既要在 DMA 再次写入前完成复制，也要保证解析结束前不复用该块。若采用有限缓冲池，还要说明消费持续跟不上时如何处理；加长指针队列不会延长原 DMA 数据的有效时间。
- 采用短时屏蔽中断来提交多个字段时，先确认该屏蔽范围能覆盖读取者，再说明相关实时任务是否允许这段推迟。保护区只做必要提交，保留原中断状态；问验证时，应说明怎样测量响应推迟并与允许的延迟比较。
- 采用双缓冲或快照发布时，说明谁写谁读、发布动作怎样保持不可分割、数据先于索引可见，以及读取结束前的复用条件。拟议方案依然是方案，不能由解释完整推断已经实现或通过实测。

这些条件是让当前建议成立的原因，不要求学员在简单确认题中背一套边界清单。

## 选型与资源限制

问选型时，要帮助学员从产品功能、接口、内存和算力需求讲出取舍，不能只纠正个别术语。

一份 LVGL 面试记录中，学员用常见 STM32 的资源情况举例，说明 MCU 资源较紧，再谈内存配置。原点评逐项追究 RAM 范围、分配器是否更安全，还加入整屏和分块缓冲的精确计算。这超出了当时的面试问题。

合适的补充是资源受限时怎么做：精简字体和图片、控制同时创建的控件数量、使用较小缓冲分块刷新。只有面试明确追问容量计算或分配器原理时，再展开这些内容。

## 解释要解决眼前的问题

- DMA 打印的简短追问，重点是串口等待为什么占用执行时间，以及 DMA 怎样减轻影响。不要自动扩展成日志队列、满队列策略和性能测试方案。
- 问存储抽象，可以用保存故障记录讲清上层调用什么、下面承担什么、换存储器时哪里需要变化。不要只罗列 SFUD、FAL、FlashDB 等名称。
- 问 UI 与业务怎样交互，就沿着一次操作说明谁发送请求、谁执行、结果怎么回到页面。模式名称不能代替流程。

## 点评也要讲得明白，篇幅够用就停

在一次软件架构复盘里，点评把通信任务、整手状态机、运动服务和约定节拍连成一长句。名称都写到了，学员仍要自己猜它们怎样衔接、为什么分开：

> N6 的通信任务接收命令，整手状态机判定，运动服务生成八轴目标，经 CAN-FD 下发；G474 在约定节拍生效并完成闭环，耗时处理不堵住动作通道

这一处可以借一次合拢动作，把协作过程和分工原因讲清：

> 这题沿着一次合拢动作讲，会更容易听懂：N6 先收到命令，检查整只手是否允许动作，再算出各电机要转到哪里，通过 CAN-FD 把目标发给 G474。G474 按固定周期读取位置和电流反馈，调整电机输出。图像处理和网络通信耗时不固定，把电机控制放到 G474，能让它按自己的周期运行，避免上层忙的时候拖慢电机控制

这段说明了接收、判断、下发、反馈怎样衔接，也解释了这样分工的原因。点评应有参考回答一样自然的讲解，不能只在参考回答里把含混的点评解释一遍。两者分别完成点评和示范的任务，不重复整段知识。

篇幅按当前缺口决定：只漏一句原因就补一句；需要说明协作过程才用一小段；复杂原理保留必要步骤。学员能说清原因、知道怎样改，就收住。不要把通俗理解成增加称呼或把句子拆得更多，也不照搬本例的芯片、参数和段落长度。

## 减少重复引用

原答已经在建议上方时，通常直接指出缺少的内容即可。比如学员说接触过 MVVM，却没有解释，可以用文件列表讲 Model 的业务数据与操作、View 的控件显示，以及 ViewModel 的界面状态和操作入口。

没有必要再把学员那句话完整引用一次，解释它哪里不好，再用整段引号包住替换话术。需要定位问题时提到必要的词句，示范回答自然另起一段。新增点评不用双引号，也不改用其他成对引号；原题、原答、自评保持原样。

## 技术核查与学员经历

技术依据用于判断建议是否成立，不在每题后附一串外部链接，也不把查到的例外都变成学员必须交代的内容。确属课程、且与当前问题相关的学习入口可以保留。

示例只能演示解释方法，不能据此替学员补上职责、参数或实测结果。助手自己写过的参考答案也不构成真实经历；助手改过的文字不能冒充用户已经逐句认可。

## 给出结论，不把核查交给学员

某份 G474 方案已明确 FOC 抢占优先级为 1、FreeRTOS 系统调用阈值为 5。点评仍写“taskENTER_CRITICAL 不一定能屏蔽 FOC，要对照实际优先级配置，并测一下关中断时间”，没有完成本来能够作出的判断。

合适的解答是代入这份方案：该 Cortex-M4 移植的任务临界区用 BASEPRI 屏蔽优先级数值 5～15，优先级 1 的 FOC 仍可抢占，所以 taskENTER_CRITICAL 保护不了任务写入的整组目标。任务可能只写完力矩、还没写模式就被打断；双缓冲完整写入后再发布索引，中断读取完整快照，才解决了这道题的数据一致性问题。

这里的 1 和 5 只属于该案例，不是其他项目的默认配置。可迁移的规则是作者先核查，再给项目结论。如果题目问怎样验证时序，则应说明测哪些时刻、如何与 PWM 装载期限比较、超期后怎样定位，而不是只留“再测一下”。

## 不纠正不存在的错误，不把项目策略说成协议要求

学员说“等八轴准备好，再用 SYNC 同步启动”。点评额外写“SYNC 不代表多个节点能绕过仲裁同时发报文”，纠正了学员没有表达过的观点；还把“先确认所有轴就绪”写得像 CANopen 每周期必须完成的握手流程。

应解释目标下发与生效的区别：同步 RPDO 可以先缓存数据，在约定的 SYNC 后处理；SYNC 提供同步基准，不负责确认每个节点收齐目标。若该动作要求八轴全部就绪，应用层可以增加目标批次和就绪反馈。学员把 CAN ID 说成无法广播的原因，才是原答中需要纠正的部分。

这类修改应同时检查点评和参考回答，防止点评已经纠正，口述里仍保留同一个错误或反复念教师提醒。

## 学员正文直接讲解，不附口径提醒

以下正反例用于作者检查，不进入学员交付正文。

| 待检查内容 | 判断与处理 |
| --- | --- |
| 正常总线预算约 41%，压力测试提高到 70%，观察命令排队和执行时间 | 保留：参数含义、条件与方法已经清楚 |
| 这里的 41% 不是实测数据，不能当成项目成绩 | 删除：额外的数据口径提醒 |
| 这些数字只能用于理解，不要说成自己测过 | 删除：换词后的同类提醒，也不允许 |
| 81 ms 对应撤去主动出力；机械停稳还受惯量和腱绳储能影响 | 保留：有用的物理含义区别 |
| 示例没有回归次数，不需要为了完整编一个次数 | 删除；直接给边界工况、记录量与通过标准 |
| 例如，收到批次 125，而执行批次仍为 124，说明目标尚未生效 | 保留：“例如”是自然讲解，不属于免责声明 |
| CAN 硬件 ACK 不代表控制器已经执行命令 | 保留：必要的协议解释，不按“不代表”机械拦截 |
| 请自己核对配置、补充实测数据后再回答 | 作者先完成能查清的判断，给出具体答案，不把缺口退回学员 |
| 为去掉提醒，把整个技术案例删成“没问题” | 不通过：提醒消失了，但教学内容也丢失了 |

检查新增正文的全部位置，不只看口述段落。用户已经删除、改短或清空的建议，按最新文档保留；不拿旧生成稿覆盖。
